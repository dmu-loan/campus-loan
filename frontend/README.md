# 프론트엔드

HTML, CSS, 일반 JavaScript로 학생용 모바일 화면 및 관리자용 데스크톱 화면을 구현합니다.
React, JSX, TypeScript를 사용하지 않습니다. Vite는 로컬 실행과 빌드에만 사용합니다.
기존 시안의 색상과 화면 구성을 참고해 기능별로 옮기는 초기 단계입니다.

## 실행

Node.js 버전은 `.nvmrc`를 확인합니다 (22.21.0).

```bash
cd frontend
npm ci
npm run dev
```

- 학생 화면: http://localhost:5173/
- 관리자 화면: http://localhost:5173/admin
- 빌드: `npm run build`
- 빌드 결과 확인: `npm run preview` (기본 포트 4173)

## 현재 범위

- 일반 JavaScript + Vite 개발 환경, lockfile 및 Node 버전 지정
- 공통 색상, 기본 스타일, 키보드 포커스 및 본문 바로가기
- 학생용 모바일 레이아웃과 관리자 사이드바·본문 레이아웃
- `/`, `/admin` 분기 및 알 수 없는 경로 안내

물품 목록과 상세 팝업은 예시 데이터로 표시합니다. 품절 물품의 상세 확인,
Escape/닫기 버튼, 팝업 종료 후 선택 버튼으로 포커스 복귀를 지원합니다.
대여 신청은 `/apply`의 체험 화면으로 구현했습니다. 이용 안내 → 정보 입력 →
내용 확인 → 체험 완료 순서이며 실제 접수·예약·서버 전송은 없습니다.
로그인·관리 기능과 API 연결은 아직 구현하지 않았습니다.
관리자 경로는 공개된 화면 시안이며 인증이나 접근 제어 기능이 없습니다.
실제 운영 데이터는 표시하지 않습니다. 현재 글꼴은 운영체제 기본 글꼴입니다.

## 폴더

```text
index.html     학생·관리자 화면 및 물품 카드·상세의 HTML template
src/
  data/items.js  화면 개발용 예시 물품
  styles/        공통 스타일과 레이아웃
  items.js       DOM으로 목록 생성, 상세 팝업 이벤트 처리
  application.js 신청 단계, 오류 안내, 확인·완료 화면
  application-validation.js 입력 정리 및 검증
  main.js        경로에 맞는 HTML template 표시
```

현재 `/`, `/admin`, `/apply`는 main.js에서 분기합니다. 링크 이동은 브라우저의 기본 동작을
사용합니다. 배포 서버는 `/admin` 같은 직접 접속을
`index.html`로 연결하는 SPA fallback 설정이 필요합니다.

화면은 HTML template을 복제하고, 데이터는 textContent로 입력하며,
동작은 addEventListener로 연결합니다. 추후 Spring Mustache에 연결할 때
HTML 구조와 일반 JS 로직을 활용할 수 있으며, 이번에는 백엔드를 수정하지 않았습니다.

## 다음 작업 순서

1. 관리자 화면별 기능
2. API 명세 합의 후 데이터 연결과 로딩·오류 처리

`src/data/items.js`는 FE 화면 개발용 데이터이며 확정된 API 응답 규격이 아닙니다.
품목, 재고, 반납 안내를 실제 운영 정보로 사용하면 안 됩니다.
품절 물품은 신청 버튼이 비활성화되고, 대여 가능 물품은 해당 물품을 선택한
신청 체험 화면으로 이동합니다. 입력 내용은 메모리에만 두며 완료 시 지웁니다.
새로고침하면 입력값이 초기화됩니다. 신청 번호나 접수 성공 안내를 만들지 않습니다.

## 3단계 입력 검증과 역할

- 학과·이름 필수 입력, 공백만 입력하는 경우 차단
- 기존 화면의 학번 숫자 8자리 및 휴대전화 형식 검증 유지
- 품절·존재하지 않는 물품 차단, 최종 확인 시 재검증
- 이전 단계로 이동할 때 입력값 유지, 오류 필드로 포커스 이동
- 학과는 임시 직접 입력이며 학부·학과 목록 및 최종 검증 규칙은 API 합의 후 연결

이효정(@wendygirl1336)은 학생 모바일 UI 및 관리자 데스크톱 UI를 담당합니다.
이채린(@Chae102)은 백엔드·DB/API 설계·대여/반납/운영 정책·외부 API 연동을 담당합니다.
FE의 입력 검증은 사용 편의를 위한 것이며 실제 접수 가능 여부와 운영 정책 판단은
백엔드 연동 단계에서 처리합니다. 이번 작업은 백엔드나 API 명세를 수정하지 않습니다.

작업 브랜치는 최신 `develop`에서 `feat/fe-작업명`으로 만들고,
검증한 변경 단위마다 `feat(fe): ...`, `chore(fe): ...` 등으로 커밋합니다.
PR 대상은 `develop`이며, `main`과 `develop`에 직접 push하지 않습니다.
브랜치 prefix는 이번 작업에서 합의한 `feat/`를 사용합니다.
